# เกณฑ์การตรวจสอบความสอดคล้อง (Conformance Checklist)

รายการตรวจสอบนี้จัดทำขึ้นสำหรับนักพัฒนาที่ต้องการสร้าง Library หรือระบบเชื่อมต่อ RLP Version 1 เพื่อให้มั่นใจว่าระบบสามารถทำงานร่วมกับมาตรฐานได้อย่างสมบูรณ์

---

## 1. ด้าน Framing และชั้น Transport

- [ ] **ขนาด Header:** ทุกเฟรมเริ่มต้นด้วย Header ขนาด 4 ไบต์พอดี (`type: u8`, `flags: u8`, `payload_length: u16be`)
- [ ] **ลำดับไบต์:** ฟิลด์ตัวเลขแบบหลายไบต์ทั้งหมดเข้ารหัสแบบ Network Byte Order (Big-Endian)
- [ ] **การประกอบ TCP Stream:** Parser สามารถจัดการกรณีข้อมูลถูกหั่นแบ่งท่อน (TCP Segmentation) และกรณีมีหลายเฟรมรวมกันใน Buffer เดียว (TCP Coalescing) ได้
- [ ] **การป้องกัน Memory:** ตรวจสอบว่า `payload_length <= maxFrameSize` ก่อนจอง Memory เสมอ หากเกินต้องส่ง `FRAME_TOO_LARGE` (4) และปิด Socket ทันที
- [ ] **การคุม Backpressure:** ฝั่งส่งจำกัดขนาดคิวใน Memory เมื่อเขียน Socket ไม่ทัน และตัดการเชื่อมต่อปลายทางที่ช้าด้วย `SLOW_PEER` (9)

---

## 2. ด้านการถอดรหัสและการตรวจสอบความถูกต้อง

- [ ] **ความเข้มงวดของ Flags:** ปฏิเสธเฟรมที่มี Flag อื่นใดที่ไม่ใช่ `0x00` บนแพ็กเก็ตทุกชนิดที่ไม่ใช่ `DATA` ด้วยข้อผิดพลาด `INVALID_PACKET` (5)
- [ ] **Flags ของ DATA:** บนเฟรม `DATA` ปฏิเสธบิตอื่น ๆ นอกเหนือจากบิต 0 (`HAS_TIMESTAMP`) ด้วย `INVALID_PACKET` (5)
- [ ] **ขอบเขตของ ValueType:** ปฏิเสธรหัสชนิดข้อมูลที่มีค่านอกช่วง `1` ถึง `13` ด้วย `UNSUPPORTED_TYPE` (7)
- [ ] **ความเข้มงวดของค่าบูลีน:** ตรวจสอบว่าค่า `BOOL` เป็น `0x00` หรือ `0x01` เท่านั้น หากพบค่าตั้งแต่ `0x02` ขึ้นไปต้องปฏิเสธด้วย `INVALID_PACKET` (5)
- [ ] **ความถูกต้องของ UTF-8:** ตรวจสอบว่าข้อความ `STRING` เป็นลำดับไบต์ UTF-8 ที่สมบูรณ์ หากผิดมาตรฐานต้องปฏิเสธด้วย `INVALID_PACKET` (5)
- [ ] **การอ่านไบต์ครบถ้วน:** ตรวจสอบว่าอ่านข้อมูลหมดพอดีตาม `payload_length` หากไบต์ขาดหรือมีไบต์เหลือต้องแจ้ง `INVALID_PACKET` (5)
- [ ] **ห้ามมี Timestamp ใน COMMAND:** ปฏิเสธแพ็กเก็ต `COMMAND` ใด ๆ ที่มีการระบุ Timestamp ด้วย `INVALID_PACKET` ("timestamp not allowed")

---

## 3. ด้าน Handshake และ State Machine

- [ ] **สถานะเริ่มต้น:** Connection เริ่มต้นที่สถานะ `WAITING_HELLO` เสมอ
- [ ] **เฟรมแรกต้องเป็น HELLO:** หากได้รับแพ็กเก็ตอื่นในสถานะ `WAITING_HELLO` ต้องส่ง `INVALID_STATE` (6)
- [ ] **ตรวจสอบเวอร์ชัน:** เซิร์ฟเวอร์ปฏิเสธ Client ที่ส่งเวอร์ชันอื่นที่ไม่ใช่ `1` ด้วย `UNSUPPORTED_VERSION` (1)
- [ ] **ห้ามส่ง HELLO ซ้ำ:** หากได้รับ `HELLO` ในสถานะ `ACTIVE` ต้องปฏิเสธด้วย `INVALID_STATE` (6)
- [ ] **การบังคับทิศทาง:**
  - เซิร์ฟเวอร์ปฏิเสธเมื่อ Client ส่ง `WELCOME` หรือ `COMMAND` ด้วย `INVALID_STATE` (6)
  - Client ปฏิเสธเมื่อเซิร์ฟเวอร์ส่ง `HELLO`, `DATA`, `BATCH` หรือ `ACK` ด้วย `INVALID_STATE` (6)
- [ ] **สถานะปิดการเชื่อมต่อ:** ปฏิเสธทุกเฟรมที่ได้รับหลังจากปิด Session แล้วด้วย `INVALID_STATE` (6)
- [ ] **Handshake Timeout:** เซิร์ฟเวอร์สั่งตัดการเชื่อมต่อทันทีหาก Client ยืนยันสิทธิ์ไม่สำเร็จภายในระยะเวลาที่กำหนด
- [ ] **หนึ่ง Session ต่อหนึ่งอุปกรณ์:** เมื่ออุปกรณ์เชื่อมต่อเข้ามาใหม่ เซิร์ฟเวอร์ต้องปิด Socket ของ Connection เดิมก่อนผูกการทำงานกับ Connection ใหม่

---

## 4. ด้าน Heartbeat และการจัดการข้อผิดพลาด

- [ ] **การตอบกลับ Nonce:** เมื่อได้รับ `PING` ปลายทางต้องตอบกลับด้วย `PONG` ที่มีค่า `nonce` เดียวกันทันที
- [ ] **การตัดการเชื่อมต่อเมื่อพบ Error:** เมื่อส่งหรือได้รับ `ERROR` ต้องปรับสถานะเป็น `CLOSED` และตัดการเชื่อมต่อทันที
- [ ] **ความปลอดภัยของข้อความ Error:** ข้อความ Error Text ต้องไม่เปิดเผยข้อมูลความลับหรือ Stack Trace ภายในเซิร์ฟเวอร์
- [ ] **การตัดการเชื่อมต่อแบบปกติ:** เมื่อได้รับ `DISCONNECT` ปลายทางต้องปิด Stream การเชื่อมต่อตามลำดับอย่างเรียบร้อย
