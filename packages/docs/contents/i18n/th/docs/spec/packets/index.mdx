# รายการ Packet Types ทั้งหมด

เอกสารนี้ระบุรายละเอียดของแพ็กเก็ตทั้ง 10 ชนิดใน RLP Version 1 ครอบคลุมโครงสร้างระดับไบต์ ทิศทางการส่งที่อนุญาต Flags ที่รองรับ และข้อมูลใน Payload

---

## ตารางสรุป Packet Types

| รหัส | ชื่อแพ็กเก็ต | ทิศทางการส่งที่อนุญาต | Frame Flags ที่รองรับ | วัตถุประสงค์หลัก |
|---|---|---|---|---|
| `1` | `HELLO` | Client $\to$ Server | `0x00` | เริ่มต้นเชื่อมต่อ ยืนยันสิทธิ์ และแลกเปลี่ยน Capabilities |
| `2` | `WELCOME` | Server $\to$ Client | `0x00` | ตอบรับการยืนยันสิทธิ์ และส่ง Server Capabilities กลับ |
| `3` | `DATA` | Client $\to$ Server | `0x00`, `0x01` | ส่งข้อมูล Telemetry ของเซนเซอร์ 1 รายการ |
| `4` | `BATCH` | Client $\to$ Server | `0x00` | ส่งชุดข้อมูล Telemetry หลายรายการในเฟรมเดียว |
| `5` | `COMMAND` | Server $\to$ Client | `0x00` | ส่งคำสั่งควบคุมหรือสั่งงาน Actuator ไปยังอุปกรณ์ |
| `6` | `ACK` | Client $\to$ Server | `0x00` | รายงานผลการทำงานของคำสั่ง Command |
| `7` | `PING` | ทั้งสองทิศทาง | `0x00` | ตรวจสอบสถานะการเชื่อมต่อ (Liveness Check) |
| `8` | `PONG` | ทั้งสองทิศทาง | `0x00` | ตอบรับการตรวจสอบสถานะการเชื่อมต่อ |
| `9` | `ERROR` | ทั้งสองทิศทาง | `0x00` | แจ้งข้อผิดพลาดร้ายแรงและยุติการเชื่อมต่อ |
| `10` | `DISCONNECT`| ทั้งสองทิศทาง | `0x00` | สั่งตัดการเชื่อมต่อตามลำดับปกติ (Clean Teardown) |

---

## 1. Type 1: HELLO (Client $\to$ Server)

Client **MUST** ส่งแพ็กเก็ต `HELLO` เป็นเฟรมแรกเสมอหลังจากเปิดการเชื่อมต่อ TCP สำเร็จ

```
+---------------+------------------+-------------------+----------------------+
| Version (u8)  | Device ID (lp8)  | Credential (lp16) | Capabilities (lp16)  |
| 1 ไบต์        | 1 + L ไบต์       | 2 + L ไบต์        | 2 + L ไบต์           |
+---------------+------------------+-------------------+----------------------+
```

- **`Version` (`u8`):** เวอร์ชันของโปรโตคอล สำหรับ RLP v1 ฝั่ง Client **MUST** ระบุเป็น `1`
- **`Device ID` (`lp8`):** รหัสประจำตัวอุปกรณ์ในรูปแบบ UTF-8 (ความยาวนำหน้า 1 ไบต์ สูงสุด 255 ไบต์)
- **`Credential` (`lp16`):** Token หรือข้อมูลยืนยันตัวตน (ความยาวนำหน้า 2 ไบต์ สูงสุด 65,535 ไบต์)
- **`Capabilities` (`lp16`):** บิตหรือข้อมูลระบุความสามารถของ Client (ความยาวนำหน้า 2 ไบต์ สูงสุด 65,535 ไบต์)
- **Flags:** MUST เป็น `0x00` หากพบค่าอื่น **MUST** ตอบกลับด้วย `INVALID_PACKET`

---

## 2. Type 2: WELCOME (Server $\to$ Client)

เซิร์ฟเวอร์จะส่งแพ็กเก็ตนี้กลับทันทีเมื่อตรวจสอบความถูกต้องของ `HELLO` ผ่าน

```
+---------------+----------------------+
| Version (u8)  | Capabilities (lp16)  |
| 1 ไบต์        | 2 + L ไบต์           |
+---------------+----------------------+
```

- **`Version` (`u8`):** เวอร์ชันโปรโตคอลที่เซิร์ฟเวอร์ยืนยัน (`1`)
- **`Capabilities` (`lp16`):** ข้อมูลความสามารถหรือการตั้งค่าของเซิร์ฟเวอร์ (ความยาวนำหน้า 2 ไบต์)
- **Flags:** MUST เป็น `0x00`

---

## 3. Type 3: DATA (Client $\to$ Server)

ส่งข้อมูลเซนเซอร์ 1 ค่าในระหว่างที่ Session อยู่ในสถานะ `ACTIVE`

- **Flags:**
  - `0x00`: ส่งข้อมูลปกติแบบไม่มี Timestamp
  - `0x01` (`HAS_TIMESTAMP`): มีค่า Timestamp ขนาด 8 ไบต์ (`i64be` หน่วยมิลลิวินาที) แนบมาข้างหน้า Value
  - หากมีการตั้งบิตอื่น **MUST** ปฏิเสธด้วย `INVALID_PACKET`
- **Payload:** มีโครงสร้างตรงตาม [Sample Structure](/th/docs/spec/data-types#4-โครงสร้างของข้อมูลตัวอย่าง-sample-structure)

---

## 4. Type 4: BATCH (Client $\to$ Server)

ส่งชุดข้อมูลเซนเซอร์หลายรายการรวมกันใน 1 เฟรมเพื่อลด Overhead

```
+--------------------+---------------------------------------------------+
| Count (u16be)      | รายการ Sample Records ต่อเนื่องกัน (ตามจำนวน Count)     |
| 2 ไบต์             |                                                   |
+--------------------+---------------------------------------------------+
```

แต่ละ Sample Record ภายใน Batch จะมี Flag กำกับเฉพาะของตัวเอง:
```
+--------------------+-------------------+------------------+-----------------------+---------------+
| Sample Flags (u8)  | Channel (u16be)   | Value Type (u8)  | [Timestamp (i64be)]   | Value Payload |
| 1 ไบต์             | 2 ไบต์            | 1 ไบต์           | 8 ไบต์ (ถ้าบิต 0=1)   | ขนาดแปรผัน    |
+--------------------+-------------------+------------------+-----------------------+---------------+
```

- **`Count` (`u16be`):** จำนวนเรคคอร์ดภายใน Batch (`0` ถึง `65,535`)
- **`Sample Flags` (`u8`):** บิต 0 ระบุว่าเรคคอร์ดนั้นมี Timestamp หรือไม่ บิต 1–7 **MUST** มีค่าเป็น `0`
- **Frame Flags:** Flags ของเฟรมหลักภายนอก **MUST** เป็น `0x00`

---

## 5. Type 5: COMMAND (Server $\to$ Client)

เซิร์ฟเวอร์ส่งคำสั่งสั่งงานไปยังอุปกรณ์ Client

```
+-----------------+-------------------+------------------+-----------------------+
| ID (u32be)      | Channel (u16be)   | Value Type (u8)  | Value Payload         |
| 4 ไบต์          | 2 ไบต์            | 1 ไบต์           | ขนาดแปรผัน            |
+-----------------+-------------------+------------------+-----------------------+
```

- **`ID` (`u32be`):** รหัสคำสั่งที่เซิร์ฟเวอร์สร้างขึ้นแบบเพิ่มขึ้นต่อเนื่อง (Monotonic modulo $2^{32}$)
- **`Channel` (`u16be`):** หมายเลขช่องสัญญาณเป้าหมาย
- **`Value Type` (`u8`):** รหัสชนิดข้อมูล (`1` ถึง `13`)
- **`Value Payload`:** ข้อมูลค่าของคำสั่งที่ต้องการสั่งงาน
- **ข้อห้ามเรื่อง Timestamp:** คำสั่ง COMMAND **MUST NOT** (ต้องไม่มี) Timestamp โดยเด็ดขาด หากตัวถอดรหัสพบ Flag มี Timestamp ผู้รับ **MUST** ปฏิเสธด้วยข้อผิดพลาด `INVALID_PACKET` ("timestamp not allowed")

---

## 6. Type 6: ACK (Client $\to$ Server)

Client รายงานสถานะการทำงานของคำสั่งกลับมายังเซิร์ฟเวอร์

```
+-----------------+-------------------+
| ID (u32be)      | Status (u8)       |
| 4 ไบต์          | 1 ไบต์            |
+-----------------+-------------------+
```

- **`ID` (`u32be`):** ตรงกับรหัสคำสั่ง (Command ID) ที่ต้องการยืนยัน
- **`Status` (`u8`):** รหัสสถานะการทำงาน:
  - `0`: `OK` — ดำเนินการสำเร็จ
  - `1`: `REJECTED` — อุปกรณ์ปฏิเสธการรันคำสั่ง
  - `2`: `UNSUPPORTED` — อุปกรณ์ไม่รองรับ Channel หรือ ValueType นี้
  - `3`: `FAILED` — เกิดข้อผิดพลาดขณะควบคุมฮาร์ดแวร์

---

## 7. Type 7 & 8: PING และ PONG (ทั้งสองทิศทาง)

ใช้สำหรับตรวจสอบว่าคู่สนทนายังทำงานอยู่ (Heartbeat) และใช้วัดค่า Latency:

```
+--------------------+
| Nonce (u32be)      |
| 4 ไบต์             |
+--------------------+
```

- **`Nonce` (`u32be`):** ค่าตัวเลขสุ่ม 32-bit
- **กฎการ Echo:** เมื่อได้รับ `PING` ปลายทาง **MUST** ตอบกลับด้วย `PONG` ที่มีค่า `Nonce` ตรงกันทุกประการทันที

---

## 8. Type 9: ERROR (ทั้งสองทิศทาง)

ใช้แจ้งเตือนข้อผิดพลาดระดับโปรโตคอลที่ไม่สามารถกู้คืนได้:

```
+--------------------+----------------------+
| Code (u16be)       | Message (lp8)        |
| 2 ไบต์             | 1 + L ไบต์           |
+--------------------+----------------------+
```

- **`Code` (`u16be`):** รหัสข้อผิดพลาดตามตาราง [Error Codes](/th/docs/spec/errors)
- **`Message` (`lp8`):** ข้อความภาษาอังกฤษอธิบายสาเหตุ (สูงสุด 255 ไบต์)
- **พฤติกรรม:** เมื่อส่งหรือได้รับแพ็กเก็ต `ERROR` จะถือว่า Session เปลี่ยนเป็นสถานะ `CLOSED` และจะต้องยุติการเชื่อมต่อทันที

---

## 9. Type 10: DISCONNECT (ทั้งสองทิศทาง)

ใช้บอกล่วงหน้าเพื่อปิดการเชื่อมต่ออย่างเป็นระเบียบ:

```
+--------------------+
| Code (u16be)       |
| 2 ไบต์             |
+--------------------+
```

- **`Code` (`u16be`):** รหัสเหตุผล (`0` คือปิดปกติ)
- **พฤติกรรม:** เมื่อได้รับแพ็กเก็ตนี้ ฝั่งรับ **MUST** สั่งปิด Stream การเชื่อมต่อทันที
